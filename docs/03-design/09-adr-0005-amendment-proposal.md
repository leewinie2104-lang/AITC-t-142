# Proposal: amend ADR-0005 — licence-plate encryption in the application, not in PostgreSQL

- **Status**: Proposed (not accepted). ADR-0005 is unchanged until the team accepts this.
- **Date**: 2026-11-18
- **Affects**: [ADR-0005](../10-adr/ADR-0005-rds-postgres-asyncpg-rls-alembic-sql.md), "Hạ tầng DB" (pgcrypto for
  plate encryption). Decision log: [D-07](07-db-decision-log.md), with D-14 (erasure) and D-25 (LPR = sensitive).
- **If accepted**: the docs-keeper agent updates ADR-0005 (or writes a new ADR superseding that bullet; ADR-0011 is taken by the MVP simplifications and does not cover plate encryption) and
  `docs/README.md`. The schema in `docs/03-design/sql/schema.sql` already follows this proposal.

## Context

ADR-0005 enables `pgcrypto` for "mã hóa biển số" (plate encryption) and, in the v1–v3 design, ledger hashing (the ledger is deferred in v4, see [ADR-0011](../10-adr/ADR-0011-mvp-simplifications.md)). With pgcrypto the key
is sent to PostgreSQL in every encrypt/decrypt statement, e.g. `pgp_sym_decrypt(col, $key)`. The key can then
leak through:

- server logs (`log_min_duration_statement`, errors with `DETAIL`, `auto_explain`);
- `pg_stat_activity.query` while the statement runs;
- RDS Performance Insights and any query-capture tooling;
- DB backups and replicas, which hold the ciphertext *and* whatever key copies leaked into logs.

Meanwhile the Personal Data Protection Law 91/2025/QH15 and Decree 356/2025/ND-CP (in force since 2026-01-01,
replacing Decree 13/2023) ask for encryption and strict access control for sensitive data. LPR events tie a
plate to a precise place and time, and the design treats them as sensitive (D-25).

Hashing does not need pgcrypto either: PostgreSQL ≥ 11 has a core `sha256()` function (used by the v1–v3 ledger
hash chain, now deferred).

## Decision (proposed)

1. **Plates are encrypted in the application** with **AES-256-GCM** using **envelope encryption**: a data key
   is generated by AWS KMS (`GenerateDataKey`) and cached in memory for a bounded time. Only the *wrapped*
   data key and a key version are stored. Each ciphertext stores
   `version ‖ nonce (96-bit, random) ‖ ciphertext ‖ tag`; the AAD binds the row id and the column name.
2. **Lookup without decryption** uses a **blind index**:
   `plate_hash = HMAC-SHA256(normalise(plate), K_index)`. `K_index` is a separate key (KMS/SSM SecureString),
   never the encryption key. `normalise` = NFKC, uppercase, keep `[A-Z0-9]` only (one shared function used by
   registration and N1).
3. **PostgreSQL never sees a key.** The DB stores `plate_ciphertext bytea`, `plate_key_version smallint`,
   `plate_hash bytea`, `plate_masked text`. The application role cannot `SELECT plate_ciphertext` (column
   grants). The only read paths are `app.reveal_lpr_plate` / `app.reveal_vehicle_plate`, which check role and
   zone and write `plate_access_log` in the same transaction. The app decrypts what those functions return.
4. **pgcrypto stays installed** for tests and seeds and for possible later uses, but production code does not
   call `pgp_sym_*`.
5. **Key rotation**: new writes use the newest key version. A background job re-encrypts rows with
   `plate_key_version < current` in batches. Rotating `K_index` needs a full re-hash (one pass over `vehicle`;
   `lpr_event` rows age out within 90 days, D-05).
6. **Erasure** (D-14) sets `plate_ciphertext` and `plate_hash` to NULL.

## Consequences

**Positive**
- Keys never appear in DB logs, query text, monitoring or backups.
- One crypto implementation, unit-tested in Python (cryptography's `AESGCM`); KMS gives audit trails of key use.
- Equality matching for LPR (N1) works through the blind index without decrypting anything.

**Negative**
- No SQL-side search on the plaintext (no `LIKE`, no fuzzy match in SQL). Fuzzy matching of misread plates
  (FR-16a) runs in the app on the small candidate set returned by the blind index plus neighbouring reads.
- KMS latency and cost on cache misses; requires a cache with a TTL and a max-uses limit per data key.
- The blind index leaks equality (the same plate gives the same hash). Accepted: the matching feature needs
  exactly that, and the index key is separate and rotatable.
- A team member must own key rotation and the re-encryption job.

## Alternatives considered

| Option | Why not chosen |
|--------|----------------|
| pgcrypto `pgp_sym_encrypt` with key passed per statement (current ADR-0005) | Key exposure paths listed above; harder to audit key use |
| RDS storage encryption only (KMS at rest) | Already on, but protects disks and backups, not DB users or logs; does not meet "only the zone's BQL sees originals" |
| Deterministic encryption (AES-SIV) instead of a separate HMAC | One key for both searching and confidentiality; rotating it re-encrypts everything; GCM + HMAC is the more common pattern |
| Tokenisation service / vault (e.g. a separate microservice) | Too much infrastructure for a 4-person team and a demo; can be added behind the same columns later |

## Verification

- Unit tests: encrypt/decrypt round trip, wrong AAD fails, tampered tag fails, normalisation table
  (`30A-123.45`, `30a12345`, full-width digits).
- Integration test (exists in `docs/03-design/sql/seed-and-tests.sql` §8): the app role cannot select
  `plate_ciphertext`; a reveal writes `plate_access_log`; a BQL of another zone is refused.
- Operational: CloudWatch alarm on KMS `Decrypt` rate anomalies; a grep of DB logs for `pgp_sym` must be empty.
